# M4 — 桌面 UI 打磨（信息架构定稿 + 重构记录）

> 状态：2026-09-03 起，主结构已定稿并落地；UI 打磨未完，跟进项见文末与 AGENTS.md 待办。

## 背景与决策（IA：编辑器为主界面，批处理=命令弹窗）

用户对早期 UI 判断「非常混乱」：翻译/回写被做成了**嵌入的独立视图**、用 ActivityBar 图标切换，逻辑重复、结构割裂。

对照业内本地化/桌面工具公认模式（Trados/memoQ/OmegaT/MT 工具）后确定方向，**并得到 UX 调研 workflow 的佐证**：

- **主界面 = 翻译编辑器**（校对文本的地方），其他都围绕它展开。
- **批处理/导出（翻译、回写）不做常驻视图** —— 是「按钮 → 弹窗配置 → 执行」的命令操作。
- **长任务进度**：开始后收进**底部状态栏/非模态条**（可看、不锁界面、可继续校对）；完成后刷新条目。
- **导出/回写结果**：在**弹窗内报告**（成功/警告/错误），不跳页面。
- 唯一例外：**导入**是阻塞覆盖层（首步不可操作，需要强反馈）。

## 已落地的重构（前端，无协议/Rust 改动）

- [App.tsx](apps/desktop/src/App.tsx)：只渲染 Editor 主面 + MenuBar/Sidebar/StatusBar；三个操作弹窗 TranslateModal/WritebackModal/ApiKeyModal；导入进度覆盖层；启动订阅 progress 通知 → StatusBar。

- [WritebackModal](apps/desktop/src/components/WritebackModal.tsx)：填输出目录（默认源游戏旁 `_zh`）→ 回写 → 结果在弹窗内报告（写入条数/警告明细可展开/错误）；结果改本地态，每次打开重置，不留上次旧结果。

## 编辑语义（沿用 M4 正交模型，勿回退）

`status`（1待译/2机翻/4已确认）与 `edited`（1=人工改过）**正交**。机翻条目被人改后：status 仍 2、edited=1 → 命中「机翻」与「已修改」两筛；单元格显示「机翻·已改」。保存空改/未改 = no-op（待译不进已改）。参考 [EditEntryModal](apps/desktop/src/components/EditEntryModal.tsx)。

### 机翻基线 machine_text（2026-09-03）

「改过的译文不能清空回未改状态」+「机翻·已改看不到机翻内容」两个 bug 的根源是 **translation 单字段被人工覆盖**（AI 输出丢了）。修复 = 加独立基线列 `machine_text`（最近一次 AI 机翻输出）：

- AI 落库（`repo.upsert_translations` / 后端 `translate.import`）即记基线 `machine_text = translation`；纯机翻未改时两者相等，从未机翻过为 null。
- **人工编辑只改 `translation` + `edited=1`，基线天然保留** → 编辑弹窗可展开「机翻原文（AI 原文）」、一键「恢复为机翻」（translation 还原基线、edited 归 0）。
- **清空回待译**（`translation=null,status=1`）：基线一并清掉（无译文就无「机翻原文」可言，防陈旧 AI 原文在后续直填时误触发恢复块）。状态机放行单次 MACHINE→PENDING（CONFIRMED 仍不可逆）。
- 语义封装在 [repo.py](core/gt_core/project/repo.py)（`update` 里 null-清空规则 + `upsert_translations` 就地覆写）与 [EditEntryModal](apps/desktop/src/components/EditEntryModal.tsx)（canRevertMachine/canClear 判定）。

## 模型 API 面板（2026-09-03，两轮重做）

按业内实践重做「添加大模型 API」面板，并修掉连通性测试 ~5s / ~9s 的问题（用户要 CC switch 式即时反馈）：

- **~5s 根因**：旧 `providers.test` 发**真实生成请求**验证「能否翻译」；DeepSeek 等端点不支持
  json_schema → `_post` 先发 structured 再降级 json_object，**连做两轮生成推理** → 误报连接延迟。
  改成零推理 `GET /models` 后仍 ~9s：**第三方中转 /models 响应也要等慢服务端 TTFB**，本质是服务端
  响应慢，不是网络不通。两轮验证逼出结论——**连通性 ≠ HTTP 往返**。
- **最终语义 = TCP/TLS ping**：`test()` 现在只做 `asyncio.open_connection` 握手（`happy_eyeballs`
  并行 v4/v6），零 HTTP 往返，4s 上限；错误分类（超时/拒连/证书/DNS/地址无效）。实测 api.deepseek.com
  **146ms 即通**。key/余额（401/402/403）不再在连通检查暴露——那是「拉模型列表」那一步的事
  （`list_models` 原样保留，供 UI 分步）。参考 [openai_compat.py](core/gt_core/providers/openai_compat.py)
  `_endpoint`/`_connect`/`test`。`base.py` `test` 契约文档同步改为 ping 语义。
- **界面分两步**：① 测试连接（ping 秒回显示「已连接 · xx ms」）→ 通过后自动异步拉取模型列表
  （独立 spinner，「拉取模型中…」，拉取慢/失败不再伪装成连接慢，401/402/403 在这步以琥珀色提示）；
  端点无 /models 可手输模型名保存，另有「重试拉取」。
- **模型选择（踩三坑后定稿 = chip 平铺，弃弹层）**：WebView2 下 `<input list=datalist>` 弹层滚不动；
  `position:absolute` 下拉被弹窗 `overflow:auto` 滚动容器裁剪/抢滚轮（「弹窗滑动影响可选模型滑动」）；
  文档流内滚动下拉在折叠线附近仍可能露不全。三个都试过仍不稳 → **彻底不依赖弹层**：[ModelPicker](apps/desktop/src/components/ApiKeyModal.tsx)
  把可用模型渲染成**输入框下方的内联 chip 按钮，始终平铺**，点哪个选哪个（3 个模型就是 3 颗可见钮，
  无滚动参与）；输入框仍可手输自定义模型名；模型 >12 个（本地 LM Studio）才限高内滚
  （`overscrollBehavior: contain` 防滚轮连锁弹窗）。
- **常见服务预设 chips**（DeepSeek/OpenAI/Kimi/GLM/Qwen/豆包/Ollama/LM Studio）一键填名称+地址；
  key 显示/隐藏；已配置服务卡片「测试连接」+「删除」（删除是原生按钮两次点击确认，`ui.Button` 无 onBlur）。
- **协议**：新增 `providers.remove`（删除服务，幂等）；给 `providers.test`/`providers.models` 参数补
  `base_url` 字段（前端保存前测临时配置一直在传，协议文档此前漏记）。「只加不改不删」纪律内。
- 数据在 `~/.gametr/providers.json`（MVP 明文，正式版 keyring）。
